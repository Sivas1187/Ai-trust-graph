# Changelog

All notable changes to this repository are recorded here. This changelog tracks the **repository** (structure, formatting, governance files, and cross-artifact consistency work) — it is not a substitute for the semantic-versioning history of each individual artifact, which is owned by that artifact's own front matter and, going forward, by the change-control process in [Artifact #11 §2](docs/11-governance-and-certification-model.md).

### Changed
- **Bundle `1.0-rc.4` — MQ-003: component-specific evidence sufficiency and evidence support ceiling (Major semantic change).** Resolves [issue #5](https://github.com/Sivas1187/Ai-trust-graph/issues/5) (MQ-003, Owner Decision 1); see `REVIEW_FINDINGS.md`, R-24.
  - **No bundle grade** (Artifact #6 §1.9): an EvidenceItem keeps its individual grade; a bundle has no grade and is never assigned the maximum, minimum, average or any aggregate of member grades; multiplicity never raises a grade or ceiling. Item-level grade changes follow Artifact #6 §1.10.
  - **Evidence Sufficiency Decision** (new Artifact #6 §4.13): a profile of the existing Assertion and Decision, referenced through `subject_assertion_id`, with `numeric_determination_supported`, `support_ceiling` and dispositions restricted to approve / condition / reject / defer. No new ontology class, predicate or state namespace.
  - **Supported components** (Artifact #4 §1.5): supported component = min(observed, approved ceiling) only where a numeric determination is supported; a normative execution order; the MQ-002 compatibility columns now mean supported component scores. Artifact #4 §1.8 is a global grade-based upper bound set by the strongest materially relied-upon SUPPORTS or CORROBORATES item, never an entitlement; absence of a linked EvidenceItem is not an E0 item.
  - **Evidence ladder** (Artifact #6 §§4.1-4.5, A.3): design E3+; implementation (any score 0-5) E4+ from the deployed or configured environment, clarified for governance and process controls; operating effectiveness E5-quality, favourable or adverse; any component score of 5 or adaptive claim repeated E5-quality. Critical: representative E5 with path context. Systemic: E5-quality plus independent validation and resilience analysis.
  - **Metrics** (Artifact #4 §§2.5, 3.3-3.5, 3.7, 5.1, 6.1-6.2, 6.8, A.1-A.2): DCA and determinate coverage use finalized final supported overall; VCR counts finalized 4-5; technical-evidence coverage requires a current approved sufficiency decision; `highest_grade` renamed `highest_member_grade` (informational only). F-03 remains generic.
  - **`Implemented - Effectiveness Limited`** meaning clarified to the evidence-supported operating-effectiveness result (Artifacts #2 §7.3, #12 §10.6, reproduced in #13).
  - **Artifact #7 / #9** workflow and presentation wording aligned. **Artifact #10**: RA-01 to RA-12 preserved as immutable historical snapshots (§0.16); new Appendix B.5 evidence-sufficiency calibration vectors. **Artifact #13**: evidence queries rewritten as inventories; missing linked evidence stays NULL, never E0 or UNKNOWN.
  - **Release class:** Major semantic change under Artifact #11 §2.3. Versions: #2 `2.0.0` → `3.0.0`; #4 `2.0.0` → `3.0.0`; #6 `1.0` → `2.0.0`; #7 `1.0` → `1.1.0`; #9 `1.0` → `1.1.0`; #10 `1.0` → `2.0.0`; #12 `2.0.0` → `3.0.0`; non-normative #13 `0.3.0` → `0.4.0`. [METHODOLOGY_MANIFEST.md](METHODOLOGY_MANIFEST.md) bumps the bundle identifier from `1.0-rc.3` to `1.0-rc.4` and re-pins those artifacts. Artifacts #3, #5, #8 and #11 are unchanged.
  - **Compatibility/migration:** Records produced under 1.0-rc.3 or earlier remain tied to that bundle and are not rewritten. Under 1.0-rc.4, no sufficiency decision, ceiling or supported score is created automatically from linked grades, `highest_grade` or any aggregate of grades; every finalized numeric component requires an approved Evidence Sufficiency Decision. Supported scores and DCA, VCR and technical-evidence-coverage figures computed under earlier readings are recomputed only in a new run; the prior run is preserved (SC-INV-09). `Implemented - Effectiveness Limited` records whose operating effectiveness cannot be supported numerically require a reviewer re-determination (UNKNOWN or Inconclusive) as a superseding record, with confidence Not rated where evidence cannot support a determinate conclusion. Historical `highest_grade` values remain as recorded; new records use `highest_member_grade`, which is informational only. Artifact #10 cases RA-01 to RA-12 are preserved as historical snapshots and are not reverse-engineered into component observations or sufficiency decisions; current calibration is Appendix B.5. Schemas, tools and generated registries must add Evidence Sufficiency Decision support and regenerate from the rc.4 source.
- **Bundle `1.0-rc.3` — MQ-002: ControlConclusionState compatibility and ninth conclusion (Major semantic change).** Resolves [issue #4](https://github.com/Sivas1187/Ai-trust-graph/issues/4) (MQ-002); see `REVIEW_FINDINGS.md`, R-23.
  - Adds the ninth control conclusion `Implemented - Effectiveness Limited` — "Implementation is established within the assessed scope; operating effectiveness has been assessed and is below the level required for Verified Effective." — immediately after `Implemented - Effectiveness Not Verified` in Artifact #2 §7.3, Artifact #12 §10.6 and Artifact #5 §0.8, and in the vocabulary reproduced in non-normative Artifact #13. Enumeration order does not imply an ordinal score. `Partially Implemented` is not broadened.
  - Artifact #12 §11.1 registers `ControlConclusionState` as a distinct state namespace.
  - Artifact #4 §1.5 adds the nine-row conclusion-to-score compatibility rule. Compatibility is checked against the final supported overall score after evidence support/caps and critical-gate treatment; incompatible records are rejected, never normalized, overridden or auto-converted. Artifact #4 §0.5 separates the scoring-result vocabulary from `ControlConclusionState`, and §1.9 notes that the 4/4/0/E5 example is compatible with `Implemented - Effectiveness Limited` without deriving the conclusion from the score.
  - Artifact #13 §3.7.2 and §3.7.5 are rewritten as linked test-result inventories. A `Test.result` is not a `ControlConclusionState`; an absent test result remains NULL and is never replaced with `Not Tested`, `UNKNOWN` or any canonical state.
  - Stale version wording inside the changed artifacts is corrected, including the Artifact #2 and #12 footers missed by the `1.0-rc.2` change and the Artifact #2 release-checklist and Artifact #4 §5.8 wording (now version-neutral). References to methodology/bundle v1.0 are unchanged. Stale cross-artifact version references in artifacts not otherwise changed here are left for a separate patch-level follow-up finding.
  - **Release class:** Major semantic change under Artifact #11 §2.3 (result states): adding a value to the closed `ControlConclusionState` enumeration and constraining conclusion compatibility breaks semantic compatibility. Artifact versions: #2 `1.1.1` → `2.0.0`, #4 `1.0` → `2.0.0`, #5 `1.0` → `2.0.0`, #12 `1.0.1` → `2.0.0`; non-normative #13 `0.2.1` → `0.3.0`. [METHODOLOGY_MANIFEST.md](METHODOLOGY_MANIFEST.md) bumps the bundle identifier from `1.0-rc.2` to `1.0-rc.3` and re-pins those five artifacts. The bundle identifier and artifact semantic versions are separate version scopes. The meaning text of the eight existing conclusions is unchanged; no control ID, evidence grade, maturity level, PathState, PathRole, PEI rule or scoring formula changes.
  - **Compatibility/migration:** Records produced against bundle 1.0-rc.2 or earlier remain historically tied to that bundle and are not rewritten. An implementation adopting 1.0-rc.3 MUST accept the ninth value and MUST enforce the Artifact #4 §1.5 compatibility rule at finalization. No record is automatically remapped to `Implemented - Effectiveness Limited` or to any other conclusion; an rc.2 record that is incompatible under the rc.3 rule, or that describes implemented but insufficiently effective operation, requires a reviewer re-determination recorded as a new, superseding record with its own evidence and rationale. Planned remediation, target dates and management acceptance do not change a conclusion or score (Artifact #4 §1.10). Schemas, tools and generated registries that enumerate `ControlConclusionState` must be regenerated from the rc.3 source. Evidence sufficiency for a numeric supported score remains open under [issue #5](https://github.com/Sivas1187/Ai-trust-graph/issues/5) (MQ-003).
- **Bundle `1.0-rc.2` — formal control-conclusion casing normalized from `Unknown` to `UNKNOWN`** for cross-artifact consistency. The control-conclusion value is now written `UNKNOWN` in Artifact #2 §7.3 (Control state and dependency) and Artifact #12 §10.6 (Control conclusion states), matching Artifact #5 §0.8. The same value is aligned in the vocabulary reproduced in non-normative Artifact #13. `UNKNOWN` is the exact canonical non-numeric assurance token for unresolved assurance due to absent, insufficient or materially conflicting evidence. It remains non-numeric and is never coerced to zero, fail, safe, Not Applicable, low risk or any other numeric or result state. **This is a conformance/casing correction only, with no semantic, scoring, evidence, maturity, path or governance change.** Ordinary prose and canonical titles that use the English word "Unknown" (e.g. `D1.5 Unknown, orphan and lifecycle management`) are unchanged, as is the reachability-form value `Unknown` in Artifact #2 §6.1, which is not a control conclusion. [METHODOLOGY_MANIFEST.md](METHODOLOGY_MANIFEST.md) bumps the bundle identifier from `1.0-rc.1` to `1.0-rc.2` and re-pins the Git blob SHAs of Artifacts #2, #12 and #13. Per Artifact #11 §2.3 (a patch change is a defect, typo or non-semantic clarification), the affected artifacts receive patch-version increments: Artifact #2 `1.1` → `1.1.1`, Artifact #12 `1.0` → `1.0.1`, Artifact #13 `0.2` → `0.2.1`. All other artifact versions are unchanged.
  - **Compatibility/migration:** Existing records produced against bundle 1.0-rc.1 using the formal ControlConclusionState token "Unknown" remain historically tied to that bundle. An implementation explicitly migrating such records to 1.0-rc.2 may translate that control-conclusion token to "UNKNOWN". No reassessment, score change or semantic reinterpretation is implied.
