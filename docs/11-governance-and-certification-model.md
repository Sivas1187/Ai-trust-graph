# 0.5  Constitutional invariants

The invariants below override commercial pressure, schedule, popularity, tool convenience and founder preference.

| **ID** | **Invariant** |
| --- | --- |
| GOV-INV-01 | Canonical meaning cannot be changed by a tool implementation. |
| GOV-INV-02 | Commercial revenue cannot influence technical or certification decisions. |
| GOV-INV-03 | UNKNOWN remains visible and cannot be certified away. |
| GOV-INV-04 | A high score cannot override a critical gate. |
| GOV-INV-05 | Certification scope cannot exceed assessed scope and evidence period. |
| GOV-INV-06 | Training and certification decisions require managed impartiality. |
| GOV-INV-07 | Appeal review cannot be performed by the original decision maker alone. |

# 1.1  Governance operating model

The structure separates stewardship, technical authority, certification decisions, impartiality oversight, appeals and administration.

| **Body** | **Primary accountability** |
| --- | --- |
| Methodology Steward | Custody of canonical artifacts and roadmap; no unilateral certification decision. |
| Governance Council | Approves policy, major releases, scheme boundaries and appointments. |
| Technical Architecture Board | Protects conceptual, ontology, control, evidence and scoring integrity. |
| AI Security Review Board | Challenges threat, authority, validation, resilience and unsafe-use implications. |
| Certification Scheme Committee | Maintains certification requirements, scope, competence and surveillance rules. |
| Impartiality Committee | Monitors threats to impartiality and has escalation rights. |
| Appeals Panel | Reviews contested decisions independently of the original decision chain. |
| Secretariat | Manages records, notices, minutes, registers and publication operations. |
| Maintainers | Implement approved changes and repository releases. |
| Community Contributors | Propose issues, evidence, cases and extensions without approval authority. |

# 2.3  Semantic versioning

Major changes break compatibility; minor changes add backward-compatible capability; patch changes correct defects without intended semantic change.

| **Version change** | **Trigger** | **Migration** |
| --- | --- | --- |
| Major | Breaking semantics, formula, control IDs, result states or certification requirements | Formal migration and compatibility break |
| Minor | Backward-compatible controls, examples, fields or guidance | Adoption plan and declared compatibility |
| Patch | Defect, typo or non-semantic clarification | Correction note; reassess only if conclusion affected |
